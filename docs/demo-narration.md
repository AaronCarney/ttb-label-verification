This is a TTB-style label compliance prototype. A reviewer drops an alcohol label image into the page, the system extracts the fields it can read, runs the regulatory rule pack, and returns a single disposition with full citations. We are about to walk through six fixtures end to end, in five minutes.

The first fixture is a clean spirits label. I drop the image in. Within a couple of seconds, the verdict comes back as pass. Every field on the right shows a green check, and each one is backed by a citation chip that points to the specific regulation we are matching against. Class and type, brand, ABV, net contents, government warning, country of origin, address. Nothing is hand-wavy. Every pass is anchored to a clause.

Now I move on to a second pass case. This is a bourbon label whose brand is written as Stone's Throw, with an apostrophe. Older versions of this kind of system would normalize the apostrophe away and report a brand mismatch against an application that filed Stones Throw without one. Our brand validator strips smart quotes and curly apostrophes, lowercases, and runs a fuzzy match. The disposition comes back as pass, the brand chip resolves cleanly, and the audit trace shows the normalization step.

The third fixture is a label whose mandatory heading is rendered in title case rather than the all-caps required by the regulation. The disposition is fail. The reason code in the response is WARN dot CASE dot TITLECASE, which any reviewer can search for and trace back to the rule in the rule pack. The reviewer does not have to read our minds to know why the label failed.

The fourth fixture is intentionally degraded. The image is low resolution and there is glare across the lower half. Our extractor will not silently guess. The disposition is needs review, the reason code calls out insufficient image quality, and the field-level confidence flags exactly which regions the model could not read. The reviewer is told to re-upload, not handed a fabricated answer.

The fifth fixture is the batch path. I submit a fifty-label batch in a single request. The page subscribes to a server-sent events stream, and you can watch the queue position tick down as labels finish. The first individual label completes immediately, and the lookahead window stays one ahead so the reviewer is never waiting on the worker. About two thirds of the way through, the anomaly detector fires. Five of the last ten labels failed for the same reason code, so the system surfaces an advisory in line with the stream. That is the early-warning signal a real reviewer wants when an upstream artwork file is broken.

The sixth fixture demonstrates the override path. This label has an ABV value that sits just outside the tolerance band for its class. The disposition is fail. A human reviewer who has the wider context can override that verdict in three keystrokes. I press O to open the override drawer, type the reason code, and press Enter to submit. The disposition flips, a toast confirms the save, and the audit trail picks up a new entry with the reason code, the reviewer identifier, and a timestamp. Nothing is silently overwritten. The original verdict is still in the trace.

That is the whole loop. Six fixtures, six dispositions, full citations on every pass, explicit reason codes on every failure, an explicit needs-review path when we cannot see clearly, a streaming batch path with anomaly detection, and a three-keystroke override that lands in the audit trail. Everything you just saw runs against the same Application Service we will hand to a pilot reviewer.
